# Foundry execution policy

Use this policy whenever the Foundry tool decision flow reaches documentation, resource execution, `orthanc`, mutation, or read-back work.

## Native-first execution

1. Discover the command with `orthanc_help` (group listing, command schema, or `{query}` keyword search across all groups) before the first operation.
2. Execute platform operations with `orthanc_cli` — agent-mode envelope, usage-shaped errors, verification hints, fail-closed commands explain the alternative. Do not use Foundry REST, raw `orthanc` in Bash, or another CLI in its place.
3. Read official Palantir documentation before a material decision (a connected Palantir MCP server is fine for this, read-only; the guard refuses a tool on such a server whose name does not read with plain separated words). A search snippet is not decision evidence; load the full page.
4. Search for the existing resource before creating one (`orthanc search` for titles, `resource search` within a folder).
5. Read the resource and its dependencies before modifying it.

## Branches, never main

All agent work happens on branches. The mod blocks a write with no branch in every approval mode. A write that names `main`, `master` or `HEAD` as its branch, or works on main only (`workshop module publish`), or is an ontology scenario based on main (`ontology scenario create --apply` with no `--base-branch <global branch RID>`), asks the operator in every mode, yolo too, and is blocked when the operator declines or no one can be asked.

1. Ontology: create a global branch (`global-branch create agent/<kebab-name>`) and pass its RID (`ri.branch..branch.…`) as `--branch` on every ontology write that takes one. `ontology scenario create` spells its branch `--base-branch`, and it is the same value. An ontology branch RID is not enough: only a global branch is provably not main.
2. Datasets, streams, builds, `cp`, connectivity imports, repository imports, `dataset create-from-csv`, `workshop module update`, `automate update`/`pause`/`resume` and `pipeline` sandbox/edit/publish/deploy: pass one `--branch <work branch>` (a global branch RID where the command asks for one), never `master` or `main`. A schedule's build action (`orchestration schedules create`/`replace`) names `"branchName": "<work branch>"`. Running or unpausing a stored schedule, or running an import, asks the operator when what it builds is main, names no branch, or cannot be read. Create a dataset branch with `dataset branches create <dataset> agent-<kebab-name>`.
3. Code: push to a work branch with `repository push <rid> refs/heads/<work> refs/heads/<work>` and open a pull request. Never `--allow-default-branch`, never raw `git push`.
4. Promotion is the operator's: do not merge, accept or approve proposals, deploy a global branch (`global-branch deploy`) or merge a code pull request (`repository pull-request merge`) on your own. The mod runs none of them for you outside the ladder; it does not refuse them either — a promotion lands through a proposal, never directly on main, so in `yolo` it runs with no ask and in the other modes it follows the ladder (what the manifest marks `operator_approval` asks). A release tag (`repository tag create --apply`) asks the operator in every mode: run it with orthanc_cli, and the operator approves or declines it in the dialog. In yolo only a tag with `--branch <global branch RID>` runs at once. A write the agent manifest marks `operator_approval` asks the same way; in yolo it runs at once only when its `operator_approval_scope` shows it lands on one global work branch. `ontology object-upsert`, `object-upsert-batch` and `action-apply-with-overrides` cannot take a branch, so agents do not run them.

5. Writes go through `orthanc_cli` only. Bash may run Orthanc reads; an Orthanc write in Bash, in any wrapping, is blocked. Three commands Orthanc labels `read-only` write **this machine** instead of Foundry, and the mod judges those as writes: `repository clone <rid> <dir> --force` (it deletes a non-empty target folder first), `dev-console sdk install --yes|--target <dir>` (it runs `npm` or `pip` install of the packages an application's SDK definition names), and `smoke --schedule|--unschedule` (it installs or removes a launchd job that runs the smoke checks daily at 09:00 with the default profile, and survives the session). Do not reach for any of those three to finish a read; report it to the operator. `smoke --schedule` will not install through `orthanc_cli` either: the mod runs every call on the session's stack, and the schedule refuses any profile, so the call ends in a usage error and writes nothing.
6. Writes run on the stack the operator picked with `/profile`. Do not pass `--profile`: a write that names it is blocked in every mode, because orthanc would run it on that other stack. A read may name another stack. `configure use` and `configure set-default` are blocked too: they change the stack a later session starts on. `orthanc update` (and its `--plugin`) is blocked in every mode as well, and so is `claude plugin update|uninstall|disable` naming `foundry@claude-foundry`: both replace the code the guard reads its rules from, so the operator updates Orthanc and the plugin in their own terminal.
7. A stack the operator marked read-only (orthanc `configure profile set <name> --read-only`) runs no write in any mode, yolo included. `orthanc_cli` reads the profile's `read_only` mark and refuses before the approval ladder and before orthanc starts, naming the exact call. Reads, plans and local commands run, as they do in orthanc's own gate, so preview the change: run the same mutation with `--apply` left off. A mutation with no `--apply` flag writes the moment it starts, so it is refused, and its refusal says it has no plan mode. Do not look for another path, and do not touch the mark: `configure profile set <name> --no-read-only` asks the operator, whoever the mark is on, and the plugin writes nothing in orthanc's config directory (`~/.config/foundry`, where `profile-settings.json` keeps the mark) — no file write there. A shell command that names the store, a file in it or a directory above it runs only when it is a known reader (`cat`, `ls`, `jq`, `grep`, a `find` with only tests and print actions, a `git` subcommand that writes only the repository), called by its bare name, with no variable set for it and no flag that writes or runs (`sort -o` or `--out=`, `less -o`, `find -fprint`, `git -c`). Anything else is refused, including a command the list does not know, a wrapper such as `xargs` or `nice`, and a bare redirect (`> profile-settings.json`). When the store or a path in it appears anywhere on the line, every command on the line must be a reader. A directory above the store has the same rule when a pipe, a command substitution or a loop carries it to another command. The guard spells the path as bash would in these ways: globs and bracket sets, extglob, brace sequences, `$'…'`, a backslash-newline, every `~` form, `${HOME:-…}`, `${!name}` with any operator, a nameref (`declare -n`), including a target assigned later, variables the line sets (`read` from a here-string or heredoc, and `printf -v` with `--`), and, inside a word, an unknown variable, a substitution or an inexact operator (`${HOME:0:0}`) as any text, a `cd`, and `bash -c`. It reads the line, not a running shell. It does not catch a path a script builds at run time, a whole word that is a variable set elsewhere, the output of `$(cat list)`, or a file the line reads (`xargs rm < list`). Do not try any of them; ask the operator to change the mark. `orthanc_help`'s first lines and `/profile` say which stacks are read-only; a stack `configure list` says nothing about goes to the operator rather than running blind.

## Local repository clones (orthanc-first)

Code repositories are cloned locally through Orthanc, never through raw git smart-HTTP:

1. Resolve the repository name to a RID with `orthanc search "<name>"` (Compass resources of type code repository; the RID looks like `ri.stemma.main.repository.…`).
2. Plan first: `orthanc_cli repository clone <rid> <target-dir> --dry-run` — the envelope resolves the git URL, default branch, and target without writing anything.
3. Clone: `orthanc_cli repository clone <rid> <target-dir>` (add `-b <branch>` for a non-default branch). `--force` reuses a non-empty directory by deleting what is in it first, so the mod judges it as a write: do not add it to make a refusal go away — report the directory instead.
4. Work inside the clone with absolute paths (plain git and file tools); use `orthanc repository context <rid>` for the remote tree and `orthanc repository push` / `repository pull-request *` to ship changes back.
5. Deleting the clone directory is allowed. Never print `git remote -v` for a clone: the remote URL can carry a token.

## Orthanc gaps

When Orthanc fail-closes a required operation, stop and report it: the command you needed and the error envelope. Do not substitute another tool.

`orthanc ai-fde run --apply` starts an AI FDE worker that writes with its own tools for the whole run, and the guard does not see those writes one by one. Through `orthanc_cli` it asks the operator in every mode but `yolo`, where it runs with no ask; in Bash it is refused like every Orthanc write. A plan (no `--apply`) and the other `ai-fde` commands follow the ordinary ladder. Prefer reporting AI FDE-loop work (Notepad create/update, UI-only workspace actions) to the operator unless they asked for a run.

Parse the `foundry-agent-v1` JSON envelope. Treat a nonempty `errors` field as failure, even when the process exit code is zero. Follow pagination until the required result is complete.

For a mutation, use only the explicit confirmation flag reported by the current CLI. Keep the non-interactive safety refusal intact. A refused or ambiguous mutation remains blocked.

## Dependency evidence

Before a mutation, run `orthanc dependency` for each target type it supports. Retain its graph artifact with the task evidence. Block the mutation when coverage is partial or a result requires unresolved verification. For unsupported target types, record the uncovered scope and do not claim verified dependency safety.

## Read-back and verification

After execution, read the changed resource with the strongest available tool. Then run the applicable build, preview, validation, deployment check, or smoke test. Record identifiers, command output, coverage limits, and verification results. A successful command without read-back is incomplete.
